# אפיון Yuval Control — גרסה 11

יובל גוונים • טיוטת אפיון לפיתוח • 12.10.2026

מטרת המערכת: להגדיל מכירות ורווחיות, לנהל פניות ואישורים, ולתת תצוגת
שליטה בייצור ובאספקה — תוך השארת Priority ERP כמערכת המקור להזמנות,
פקודות עבודה ומסמכים פיננסיים.

# 1. החלטות מאושרות

• Priority מנהלת הזמנות, פקודות עבודה וייצור.

• הצעות מחיר מחושבות חלקית בפריוריטי וחלקית ידנית; מסמכי הצעה מופקים
בשני הערוצים.

• התמחור משלב מטר רבוע, מספר חלקים ומורכבות העבודה.

• המפעל תומך באספקות מלאות וחלקיות; אחראי ייצור מרכז דיווחים.

• פניות חדשות מגיעות לתיבה מרכזית; המנהל מחלק אותן. ממלא מקום מופעל
ידנית וגם אוטומטית באי-מענה.

# 3. תהליך פנייה ואחריות

NEW → TRIAGE → ASSIGNED → CONTACTED → QUALIFIED → QUOTED → NEGOTIATION →
WON / LOST. זכייה אינה פותחת אוטומטית הזמנה ללא אישור לקוח ובדיקת כפילות
בפריוריטי.

כל פנייה: owner_id יחיד, next_action_at, source, customer_match, status,
priority, last_contact_at. בזמן היעדרות עוברת אחריות טיפול זמנית
ל-delegate; בעלות מקורית נשמרת לצורך דיווח.

# 4. מנגנון ממלא מקום ו-SLA

מצב ידני: המנהל מפעיל ״לא זמין״, בוחר ממלא מקום וזמני התחלה/סיום. מצב
אוטומטי: אם פנייה חדשה לא טופלה או לא שובצה 30 דקות בשעות העבודה — הודעה
לממלא המקום. לאחר 60 דקות נוספות ללא קבלת אחריות — התרעה למנהל/ערוץ
חלופי. אלה ערכי פתיחה לכיול, לא החלטות עסקיות מאושרות.

אירוע ״טופל״ יוגדר כפעולה אמיתית ומתועדת (שיבוץ + משימה או שיחה), לא רק
פתיחת כרטיס. ממלא מקום מקבל הרשאת חלוקה ומעקב, ללא גישה אוטומטית למחירי
ספקים, שכר, או אישורי הנחות חריגות. מניעת העברה כפולה באמצעות מזהה אירוע
וכלל idempotency.

# 5. אישור הצעות והעברה לפריוריטי

DRAFT → REVIEW → APPROVED_INTERNAL → SENT → ACCEPTED_CUSTOMER →
SYNC_PENDING → SYNCED → ORDER_LINKED; או REJECTED / EXPIRED. שינוי
במחיר, כמות, מפרט, גוון או תנאי אספקה מבטל אישור פנימי קודם ויוצר גרסה
חדשה.

שליחה לפריוריטי רק לאחר אישור מוסמך ובדיקת מיפוי לקוח/מק״ט/מס; יש לשמור
external_document_id, external_version, sync_state ו-idempotency_key.
במקרה timeout יש לבדוק אם מסמך נוצר ב-Priority לפני ניסיון נוסף.

# 7. אינטגרציית Priority — חוזה ראשוני

קריאה בלבד בתחילה: customers, quotes, orders, work orders,
inventory/purchase prices, delivery notes, invoices — רק אילו שנחשפים
בהרשאות והגדרות הארגון. תדירות סנכרון מומלצת לפיילוט: כל 5–15 דקות
להזמנות ותורים, ודוחות כספיים בתדירות נמוכה יותר. נדרש מיפוי API אמיתי,
גרסה, שדות חובה, מטבע, מע״מ, יחידות מידה ותאריכים.

המערכת אינה משנה הזמנה, תעודת משלוח או חשבונית בפריוריטי ללא תהליך
מאושר. שינויים עוברים דרך שרת אינטגרציה עם אימות, הרשאות, יומן אירועים,
ניטור, ומניעת כפילויות.

# 8. כללי רווחיות ותמחור

מחיר מבוסס שטח + טיפול בחלקים + הכנה/מיסוך/מורכבות + דחיפות/משלוחים,
בכפוף למינימום. העלות: אבקה נצרכת, עבודה, אנרגיה, הפסדי חומר, תיקונים,
הובלה ותקורה מוקצית. מחיר הספק ותנאי לקוח נשמרים עם תוקף והיסטוריית
גרסאות. לא להציג רווח תפעולי כוודאי עד שכל העלויות אומתו.

# 9. כללי קבלה לבדיקות (UAT)

□ פנייה אחת משני ערוצים עם אותו מזהה עסק מזוהה כחשד לכפילות ואינה יוצרת
לקוח כפול בפריוריטי.

□ מעבר ידני למצב לא זמין מייעד פניות פתוחות לממלא מקום, מבלי להעניק
הרשאות מנהל.

□ פנייה שלא טופלה במשך SLA מפעילה הודעה אחת לכל דרגת הסלמה ולא הודעות
חוזרות ללא גבול.

□ שינוי מחיר הצעה שאושרה מחזיר אותה לאישור מחדש ושומר את הגרסה הקודמת.

□ timeout לאחר ניסיון יצירת הצעה בפריוריטי אינו מייצר מסמך כפול.

□ אספקה חלקית משאירה יתרה תקינה ומבחינה בין מיוצר, תקין, נשלח וחויב.

□ מוכרת סיבת אי-סגירת הזדמנות, ומוצג שיעור סגירה לפי מקור ליד.

# 10. סדר בנייה

Sprint 0: ראיון פריוריטי, מיפוי טפסים, ייצוא נתוני דוגמה והגדרת אבטחה.
Sprint 1: משתמשים/הרשאות/תיבת פניות/שיבוץ. Sprint 2: משימות, האצלה, SLA,
התראות ודשבורד. Sprint 3: הזדמנויות והצעות, גרסאות ואישורים. Sprint 4:
חיבור קריאה בלבד ודוחות. Sprint 5+: חיבור כתיבה מבוקר, ייצור/רווחיות
ואתר/מדיה. משך כל ספרינט ייקבע עם הצוות לאחר הערכת מאמץ.

# 11. נתונים פתוחים להכרעה

שמות אנשי צוות וממלא המקום; שעות המשרד; ספי SLA; מהי חריגה במחיר וברווח;
גרסת Priority וסביבת API; מסכי פריוריטי קיימים; קבצי הצעה לדוגמה; מידע
חסר לעלות; אופן קליטת WhatsApp והסכמות שיווק; שמירת מידע וגיבויים.
