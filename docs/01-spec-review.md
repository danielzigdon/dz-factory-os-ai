## ד. התאמה ל-Priority ERP

הערה: הפרטים בסעיף זה מבוססים על ידע כללי על Priority REST API (OData). **לא נבדקו מול המערכת**, וחובה לאמת אותם ב-Sprint 0 עם יועץ Priority.

| ID | חומרה | ממצא |
|---|---|---|
| P-01 | חוסם (S4) | הגרסה, המודולים ורישיון ה-API לא ידועים (Q-05). ה-REST API של Priority מחייב רישיון API ומשתמש API. |
| P-02 | חוסם (S5) | **מניעת כפילות אחרי timeout (UAT 5):** Priority לא מספקת idempotency key מובנה. נדרש שדה מותאם בטופס ההצעה/הזמנה (למשל שדה טקסט שבו נשמר `idempotency_key`) כדי שאפשר יהיה לחפש לפני ניסיון חוזר. השדה דורש התאמה של יועץ Priority. |
| P-03 | גבוה | ל-Priority אין webhooks סטנדרטיים. הסנכרון יתבצע ב-polling לפי שדה עדכון אחרון (אם הוא חשוף בטפסים) או דרך BPM/תוכניות. צריך לאמת את קיום השדה בכל טופס. |
| P-04 | גבוה | שמות טפסים צפויים (לאימות): `CUSTOMERS`, `CPROF` (הצעות מחיר), `ORDERS`, `SERIAL` (פקודות עבודה), `DOCUMENTS_D` (תעודות משלוח), `AINVOICES`/`CINVOICES` (חשבוניות), `LOGPART` (מק״טים). |
| P-05 | גבוה | מגבלות קצב ועומס: polling כל 5–15 דקות על כמה טפסים. צריך לבדוק מגבלות ועומס מול המערכת החיה. ביצוע ראשון רק מול סביבת בדיקה (Q-06). |
| P-06 | בינוני | מיפוי לקוח: `priority_customer_id` הוא UNIQUE NULLABLE. צריך להחליט מי יוצר לקוח חדש ב-Priority ומתי. לפי UAT 1 אסור ליצור כפילות ב-Priority. |
| P-07 | בינוני | מטבע, מע״מ, יחידות מידה ואזורי זמן: Priority שומרת תאריכים בשעון מקומי. המערכת תשמור ב-UTC ותמיר במקום אחד בלבד (adapter). |
